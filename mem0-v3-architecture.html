Mem0 OSS · v3 pipeline · commit a488e190

Two paths, three stores, one scope key

Everything in Mem0 v3 is either the ADD path writing memories down or the SEARCH path reading them back. filters decides whose memories either path may touch. Every block below is annotated with what it does and where it lives.

01

Where the two calls actually sit

Mem0 has no session concept, no login hook and no background worker. It is called at exactly two points per turn and is dormant everywhere else. Nothing is created when a user arrives — a partition begins to exist the first time a row is written into it.

mem = Memory.from_config({...})          # once at boot, shared

# ---- per turn ----
hits  = mem.search(user_msg, filters={"user_id": uid})
ctx   = "\n".join(f"- {h['memory']}" for h in hits["results"])
reply = my_llm(f"What we know:\n{ctx}\n\nUser: {user_msg}")

mem.add([{"role": "user",      "content": user_msg},
         {"role": "assistant", "content": reply}], user_id=uid)

The identity keys and their natural lifetimes

KeyComes fromChanges when
user_idyour auth or user tablenever, for a given person
agent_idyour configurationnever, per bot
run_idyou mint it — uuid, ticket id, thread ideach new conversation

Note the call shape differs: the parameter literally named filters exists only on search() and get_all(). add() takes the same identifiers as top-level keyword arguments. Both converge on one internal filter dict.

Do not put run_id in a search filter. It would restrict results to the current thread, which defeats long-term memory. Scope reads by user_id alone.

The run_id trade-off on writes

At main.py:924 the internal filter used by ADD is built from all three identity keys, and that dict drives both the P1 dedup lookup and the P7 entity lookup. Passing run_id therefore narrows far more than it appears to.

Effectrun_id passed to add()run_id omitted
Message log bucket
P0 / P8		 Per conversation — clean context Shared across threads; yesterday's messages can leak into today's extraction
Dedup lookup
P1		 Only sees this thread — cross-conversation duplicates slip through Sees everything
Entity index
P7		 A separate node per conversation — one entity duplicated N times One node, links accumulate
Search results Unaffected either way, as long as reads filter on user_id only
Recommendation

Omit run_id unless you need per-conversation deletion or audit. A fragmented entity index directly weakens the boost signal and duplicates accumulate — both cost more than a slightly stale ten-message buffer.

If you do need thread identity, put it in metadata instead: add(msgs, user_id=uid, metadata={"thread": run_id}). You keep the ability to filter on it without fragmenting dedup or entities, because metadata keys are not part of the identity scope.

02

What filters actually is

filters is not a scoring input. It is a WHERE clause: it decides which rows are eligible, never which row ranks first. It is passed down into every store query, so exclusion happens inside the database rather than in Python.

MethodIdentity goesShape
add()Top-level kwargsadd(msgs, user_id="alice")
delete_all()Top-level kwargsdelete_all(user_id="alice")
search()Inside filterssearch(q, filters={"user_id": "alice"})
get_all()Inside filtersget_all(filters={"user_id": "alice"})
Guard worth knowing

Identity keys inside metadata are stripped before the write template is built (_strip_identity_keys(), main.py:143). A stray metadata={"user_id": "bob"} loses that key rather than writing into Bob's partition.

03

The two paths over three stores

State lives in exactly three places. The absent arrow matters: SEARCH never reads the message log, because raw conversation is an extraction input, not a retrieval target.

04

ADD path — one LLM call, append only

Two layers. add() at main.py:760 only validates arguments and dispatches — it touches no store. All nine phases live in _add_to_vector_store() at main.py:879.

Every block explained

BlockWhat happensWorth knowing
P0 · Contextmain.py:919–921 Flattens the identity triple into a sorted, percent-escaped session scope string, then pulls the 10 newest messages stored under it. New messages are flattened into one text blob. This is what lets the extractor resolve pronouns — "I went back again" is unextractable without the previous turn. Retention of 10 is hardcoded in storage.py:279.
P1 · Existingmain.py:925–938 Embeds the flattened conversation and runs a plain vector search for the 10 nearest existing memories. Their UUIDs are replaced with "0", "1", … before the LLM sees them. This is a raw vector_store.search(), not the public search() — no BM25, no entity boost, no fusion. The remap exists so the model cannot invent plausible-looking UUIDs.
P2 · Extractionmain.py:942–984 One call. System prompt is ADDITIVE_EXTRACTION_PROMPT (prompts.py:468–944); the user side is assembled by generate_additive_extraction_prompt() at prompts.py:1016. The model emits linked_memory_ids, but the OSS writer never persists it — only attributed_to survives onto the row. Three of the seven prompt input slots are also left unwired in OSS.
P3 · Embedmain.py:992–1003 All extracted texts embedded in a single embed_batch call. On failure it retries item by item; texts that still fail are dropped from the batch rather than aborting the whole add.
P4·5 · Dedupmain.py:1015–1039 MD5 of each memory text, checked against both the current batch and the hashes of the P1 results. Survivors get a spaCy lemma string written to text_lemmatized. Dedup is exact-match only. Two paraphrases of the same fact both land. That lemma field is what BM25 later matches against, so no spaCy means no keyword signal.
P6 · Persistmain.py:1045–1084 One batched insert into the memory store, plus one history row per memory. The history event is always "ADD" and old_memory is always None — no code path writes any other event.
P7 · Entitiesmain.py:1086–1190 spaCy NER plus rules over all new memory texts. Entities are normalized and merged globally, then matched against the entity store: exact text match, or vector similarity ≥ 0.95. Hits merge into linked_memory_ids; misses create a node. The whole phase sits in try/except — a failure here only logs a warning and the memories still persist. The entity store clones the memory store's config, so it cannot use a different backend.
P8 · Messagesmain.py:1193 Appends this turn's raw messages under the session scope, then deletes everything past the 10 newest. Runs even when extraction produced nothing, so the next call still has conversational context.
What is not here

The 2025 paper's second stage — scoring each candidate fact against existing memories and choosing ADD / UPDATE / DELETE / NOOP — has no counterpart. Contradictory memories coexist and reconciliation moves entirely to read time.

This is why the extraction prompt insists a memory encode its own transition — "switched from oat lattes to americanos", not "drinks americanos". With the old row still present and often ranking higher, that clause is the only thing telling a downstream model which version is current.

05

SEARCH path — one recaller, two re-rankers

The three signals are not three parallel ways in. Semantic search alone builds the candidate set. BM25 and entity matching produce lookup tables keyed by memory id, and can only add score to rows the vector search already returned.

  • semantic — the only recaller
  • BM25 — re-ranker
  • entity — re-ranker

Every block explained

BlockWhat happensWorth knowing
S1 · Query prepmain.py:1634–1635 Two spaCy passes over the raw query: lemmatize_for_bm25() for the keyword lane and extract_entities() for the entity lane. Both degrade cleanly — get_nlp_*() returns None when spaCy is missing, so lemmatize returns the text unchanged and entity extraction returns []. No exception, no warning.
S2·3 · Recallmain.py:1638–1644 Query is embedded, then handed to the vector store with top_k = max(4·limit, 60). Similarity is computed inside the database against its ANN index. Providers ignore the query string and use vectors only. Every backend must return higher-is-better scores normalized toward [0,1] (vector_stores/base.py:16), which is what makes the later addition valid.
S4·5 · BM25main.py:1647–1659 Lemmatized query goes to keyword_search(). Raw BM25 values are squashed to [0,1] by a logistic curve whose midpoint and steepness are chosen from the query's term count. Stores that do not implement it return None and the signal silently switches off. 16 of the 30 providers implement it.
S6 · Entity boostmain.py:1661–1664, 1733 Up to 8 deduped query entities are embedded and searched against the entity store on 4 threads. Matches at similarity ≥ 0.5 push a boost onto every memory id they link to. Boost is sim × 0.5 × hubDecay, and competing boosts take max rather than summing. Hub decay 1/(1+0.001·(n−1)²) stops an entity linked to thousands of memories from flattening the ranking.
S7 · Candidate setmain.py:1666–1677 Iterates the semantic results only, dropping expired payloads, and builds the list that scoring will run over. This is where recall is decided. The two score tables are never iterated — they are only ever queried by .get(id, 0.0).
S8 · Fusionutils/scoring.py Threshold drops candidates on semantic score first, then the three components are summed and divided by D. D is computed once per query, not per candidate. If any single memory hit BM25, every candidate is divided by 2.0 — including those scoring 0 on it. A row's score therefore depends on what else came back.
S9 · Formatmain.py:1689–1731 Builds MemoryItem dicts, lifts identity and role keys from payload to top level, and folds anything else into metadata. Pass explain=True to attach score_details with all three components, D, and the threshold. It is the only way to see why something ranked where it did.
Scores are not portable

Because D depends on which signals fired for this query, the same memory scores differently across queries. Compare scores within one result set; never across two.

The single idea connecting them: because ADD refuses to reconcile anything, SEARCH has to. The over-fetch, the two re-rankers, the gate placement and the adaptive divisor all exist to pick the right memory out of a store that deliberately kept all of them — and even then, the final judgement is left to whatever model consumes the results.
